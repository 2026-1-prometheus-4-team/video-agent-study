> Prometheus 2026-1 Team 4 — Video Edit Agent
> 발표 시간: 약 8분 / 한국어 / 동아리 중간 발표
> 이 문서는 "무엇을 어떤 순서로 말할지"의 기획서다. 디자인(색/폰트/모션)은 별도 Claude Design 세션이 DESIGN.md 기준으로 처리한다.

---

## 0. 이 문서를 어떻게 쓰는가

- 이 문서는 **디자인을 모르는 다른 세션(Claude Design)에 그대로 넘겨도** 슬라이드를 만들 수 있도록 자급자족적으로 작성했다. 프로젝트 맥락, 슬라이드별 들어갈 텍스트/수치, 레이아웃 의도(요소 배치 수준)까지 담았다.
- "시각/레이아웃 메모"는 **요소 배치 수준만** 적었다(좌/우, 화살표 방향 등). 구체적인 색·폰트·애니메이션은 DESIGN.md를 따르는 Claude Design이 결정한다.
- "발표 멘트 가이드"는 발표자가 그대로 읽거나 변형해서 쓸 수 있는 구어체 초안이다.
- 에셋(GIF 등)은 아직 파이프라인 실행 중이라 미확보 상태다. **마지막 "에셋 체크리스트"에 자리(placeholder) 규격**을 정의해 두었으니, 슬라이드엔 빈 자리만 잡아두면 된다.

## 1. 발표 개요

| 항목 | 내용 |
|------|------|
| 주제 | 자연어로 영상을 편집하는 AI 에이전트 (영상 편집계의 Claude Code) |
| 청중 | Prometheus 동아리원 (AI/개발 친숙, 영상 편집 전문가는 아님) |
| 목표 | (1) 우리가 만든 멀티 에이전트 구조가 왜 새로운지 (2) 지금 어디까지 동작하는지 (3) 데모데이에 무엇을 보여줄지 |
| 톤 | 기술적이되 과시 없이. 핵심 1개(격리된 sub-agent 구조)를 확실히 각인 |
| 분량 | 본문 슬라이드 11장 + 표지/마무리 = 약 13장, 슬라이드당 평균 35~40초 |

### 발표가 끝났을 때 청중이 기억해야 할 3가지 (Take-away)

1. 정적 그래프가 아니라 **LLM이 매 턴 판단하는 ReAct 루프** 구조다 (Claude Code와 같은 발상).
2. 5종 전문가 에이전트가 **완전히 격리된 컨텍스트**에서 자기 도구만 들고 일한다.
3. 분석 → 계획 → 사용자 승인 → 실행 → 검증의 **전 구간이 이미 돌아간다**(짱구 쇼츠 데모).

### 슬라이드 1 — 표지 (0:20)

**목적**: 프로젝트 한 줄 정의 + 팀 식별.

**내용**
- 프로젝트명: Video Edit Agent
- 한 줄 정의: "자연어로 영상을 편집하는 AI 에이전트"
- 보조 카피: "지루한 부분 빼줘", "가족 나오는 장면만 모아서 쇼츠로" — 말만 하면 편집된다
- Prometheus 2026-1 Team 4
- 팀원: 이성민 · 임병건 · 이은채 · 정은서
- 중간 발표 / 날짜

**시각·레이아웃 메모**: 중앙 정렬 타이틀. 보조 카피는 작게 한 줄.

**발표 멘트**: "안녕하세요, 프로메테우스 4팀입니다. 저희는 사용자가 말로 명령하면 알아서 영상을 편집해 주는 AI 에이전트를 만들고 있습니다. 'Claude Code가 코드를 다루듯, 영상을 다룬다'가 한 줄 요약입니다."

---

### 슬라이드 2 — 문제 정의 / 왜 만드는가 (0:40)

**목적**: 공감 유발. 영상 편집이 왜 에이전트에 적합한 문제인지.

**내용**
- 영상 편집은 진입장벽이 높다: 컷 편집, 자막, 자르기 타임코드 잡기 등 반복 노동
- 기존 자동 편집 툴은 "템플릿 채우기"라 의도를 못 담는다
- 하지만 편집 작업의 본질은 "이 부분 잘라줘 → 좀 더 짧게 → OK"의 **반복 대화**다 — 에이전트가 가장 잘하는 형태
- 핵심 질문: "코딩 에이전트가 되는데, 영상 편집 에이전트는 왜 안 되나?"

**시각·레이아웃 메모**: 좌측 "사람이 직접 편집(고됨)" vs 우측 "말로 시킴(에이전트)" 대비 구도.

**발표 멘트**: "영상 편집은 컷 따고 자막 맞추는 반복 작업이 대부분입니다. 그런데 이 과정은 사실 '잘라줘, 좀 더 짧게, OK' 같은 대화로 흘러가요. 이건 에이전트가 제일 잘하는 형태입니다. 코딩 에이전트가 되는데 영상 편집 에이전트는 왜 안 되겠냐, 가 출발점이었습니다."

---

### 슬라이드 3 — 핵심 컨셉: 정적 그래프가 아니라 ReAct 루프 (0:45)

**목적**: 기술적 차별점의 큰 틀. "왜 우리 구조가 다른가".

**내용**
- 기존 LangGraph 에이전트의 한계: 노드와 엣지를 미리 고정하면 **아무리 복잡해도 정적**이다. "분석→계획→실행" 고정 파이프라인은 예외 상황에 못 버틴다.
- 우리 접근: **도구를 풍부하게 만들고, LLM이 매 턴 자유롭게 조합**한다.
- 의사코드:
  ```
  while not done:
      action = llm.think(context + 지금까지의 결과)
      result = execute(action.tool_call)
      context.append(result)
  ```
- Claude Code 대응 비유 (한 표):
  | Claude Code | Video Edit Agent |
  |---|---|
  | Read (코드 읽기) | search_video_segments (분석 JSON 검색) |
  | Edit (코드 수정) | cut_video / merge (FFmpeg 편집) |
  | Bash: test (검증) | critic 노드 (결과 검증) |
  | 재시도 | LLM이 "컷 포인트 다시" 판단 → 도구 재호출 |

**시각·레이아웃 메모**: 상단에 한 줄 명제, 중앙에 의사코드 박스, 하단에 비유 표.

**발표 멘트**: "기존 에이전트 그래프는 노드와 엣지를 미리 다 정해놓습니다. 그러면 흐름이 정적이라 예상 못 한 요청에 약해요. 저희는 반대로 갔습니다. 도구를 풍부하게 만들어 두고, LLM이 매 턴 상황을 보고 어떤 도구를 쓸지 직접 판단합니다. Claude Code가 코드를 읽고-고치고-테스트하며 스스로 도는 것과 똑같은 구조예요."

### 슬라이드 4 — 전체 파이프라인 한눈에 (1:00) [핵심]

**목적**: 시스템 전체 흐름을 한 장으로. 이후 슬라이드들이 이 그림의 부분 확대.

**내용** (5노드 그래프 — 이 텍스트 그대로 다이어그램화)
```
사용자 요청
   ↓
[analysis]        영상 사전 분석 → VideoContext (씬/대사/볼륨)
   ↓
[script]          자연어 → 단계별 편집 plan(JSON) 생성
   ↓
[interrupt_gate]  사용자 승인 / 수정 피드백  ← 사람이 개입
   ↓
[supervisor]      ReAct 루프, 전문가 에이전트 5종 spawn
   ├─ edit_expert     자르기, 합치기, 구간 검색
   ├─ audio_expert    음성인식, TTS, BGM, 효과음, 믹싱
   ├─ text_expert     자막, 타이틀, 캡션
   ├─ effect_expert   Remotion 이펙트
   └─ research_expert 트렌드, 웹검색, 컨셉
   ↓
[critic]          PASS / RETRY 검증  → 실패 시 supervisor로 되돌림
   ↓
최종 mp4 산출
```

**시각·레이아웃 메모**: 세로 플로우. `interrupt_gate`(사람 개입)와 `critic`(RETRY 화살표가 supervisor로 되돌아감)를 시각적으로 강조. supervisor에서 5개 expert로 뻗는 가지.

**발표 멘트**: "전체 흐름은 5단계입니다. 먼저 영상을 사전 분석해서 컨텍스트를 만들고, 사용자 명령을 단계별 편집 계획으로 바꿉니다. 그 계획을 사용자에게 한 번 보여주고 승인을 받아요. 승인되면 supervisor가 5종 전문가 에이전트를 불러 실제 편집을 돌리고, 마지막에 critic이 결과를 검증합니다. 통과 못 하면 다시 돌아갑니다. 이제 각 단계를 짧게 보겠습니다."

### 슬라이드 5 — 사전 분석: 4엔진 병렬 (0:50)

**목적**: 분석 단계의 깊이를 보여줌. 우리가 영상을 "이해"한다는 근거.

**내용**
- 영상이 들어오면 **4개 엔진이 병렬**로 분석하고 타임스탬프 기준으로 합친다.
  - Whisper API — 단어 단위 타임코드 (ms 정밀도)
  - Gemini — 영상 통째 업로드, 씬 경계·행동·감정·에너지
  - Claude Vision — 씬별 키프레임 객체/제스처/표정 디테일
  - FFmpeg — 침묵 감지 + 구간별 볼륨 프로필
- 결과는 VideoContext에 통합: 씬(scenes) + 대사(transcript) + 메타
- 실측 예시(레퍼런스 영상 14분 45초): 단어 351개 / 씬 37개 / 등장인물 20명 / 하이라이트 후보 6개
- 각 엔진은 못 하는 게 다르다 → 합쳐야 "차가 있다"가 아니라 "운전자가 오른손을 운전대에 올리고 전방을 본다"까지 잡힌다

**시각·레이아웃 메모**: 좌측 "영상 입력" → 4갈래로 병렬 분기 → 우측 "VideoContext로 통합". 4엔진은 카드 4개.

**발표 멘트**: "편집을 잘하려면 영상을 잘 이해해야 합니다. 저희는 한 영상을 4개 엔진으로 동시에 분석해요. Whisper로 단어별 타임코드, Gemini로 씬과 흐름, Claude Vision으로 프레임 디테일, FFmpeg로 침묵과 볼륨. 엔진마다 잘하는 게 달라서, 합치면 '차가 있다' 수준이 아니라 '운전자가 전방을 본다'까지 잡힙니다."

### 슬라이드 6 — 계획 생성 + 사람의 승인 (Human-in-the-Loop) (0:45)

**목적**: "바로 실행" 안 하고 계획을 먼저 보여주는 UX의 핵심.

**내용**
- script 노드: 자연어 요청 → **단계별 편집 plan(JSON)**. 각 step = (expert, action, 대상).
- 모호한 요청엔 plan에 **질문(questions)**을 같이 담아 사용자에게 되묻는다.
- interrupt_gate: LangGraph `interrupt()`로 그래프를 **멈추고** 사용자 승인/수정 피드백을 받는다.
  - 승인 → supervisor로
  - 수정 피드백 → script 재생성 (피드백 반영)
- 영상 편집은 "한 방에 완벽"이 거의 없다 → 이 승인 루프가 곧 UX
- (실제 짱구 케이스에서 자동 생성된 질문 예시)
  - 자막 스타일을 직접 정할지 / 자동 생성할지
  - 피아노 BGM을 넣을지
  - 9:16 변환 시 자동 크롭 vs 레터박스

**시각·레이아웃 메모**: 좌측 plan(JSON 카드 또는 step 리스트), 우측 사용자 승인/수정 분기 2갈래.

**발표 멘트**: "사용자 명령이 들어오면 바로 자르지 않습니다. 먼저 '이렇게 편집할 계획입니다'를 단계별로 만들어 보여주고, 애매한 부분은 거꾸로 질문합니다. 자막을 직접 쓸지 자동으로 할지, BGM을 넣을지 같은 거요. 사용자가 승인하면 그때 실행에 들어갑니다. 편집은 한 번에 완벽할 수가 없어서, 이 확인 루프 자체가 핵심 사용성입니다."

---

### 슬라이드 7 — Supervisor + 격리된 전문가 에이전트 (1:00) [핵심]

**목적**: 우리 구조의 진짜 차별점. 이 한 장이 가장 중요.

**내용**
- supervisor는 ReAct 루프를 돌며 전문가를 **도구처럼 호출(spawn)**한다.
- 핵심 설계 원칙: **각 sub-agent는 완전히 격리된 컨텍스트에서 실행**된다.
  - parent의 대화 기록을 **못 본다**
  - 오직 supervisor가 건네준 `task` 문자열로만 정보를 받는다
  - 자기 역할의 **도구 그룹만** 장착된다 (다른 도메인 도구 접근 불가)
- 왜 격리하나: 기존 handoff 방식은 메시지 기록을 공유해 비용·혼선이 크다. 격리하면 각 전문가가 자기 일에만 집중하고, 컨텍스트가 깨끗하다.
- 폭주 방지 가드레일: spawn 깊이 ≤ 2 / 동시 child ≤ 5 / child당 tool call ≤ 12
- 한 번의 호출 흐름:
  ```
  supervisor가 edit("0~10초 잘라 clip.mp4로 저장") 호출
    → edit_expert 새로 생성 (빈 컨텍스트)
    → [cut_video, merge_video, ...] 도구만 장착
    → task 문자열만 입력으로 받음
    → 자체 ReAct 루프로 cut_video() 실행
    → 결과 string 반환 → supervisor
    → edit_expert 소멸
  ```

**시각·레이아웃 메모**: 중앙 supervisor, 아래로 5개 expert 박스. 각 expert를 "격리 캡슐" 느낌으로(경계선) 구분. 우측에 가드레일 수치 3개를 작은 배지로.

**발표 멘트**: "여기가 저희 구조의 핵심입니다. supervisor가 전문가를 부를 때, 전문가는 완전히 빈 상태로 새로 태어납니다. 부모의 대화 기록을 전혀 못 봐요. supervisor가 넘긴 task 문장 하나, 그리고 자기 도메인 도구만 가지고 일합니다. 끝나면 결과만 돌려주고 사라집니다. 이렇게 격리하면 각 전문가의 컨텍스트가 깨끗하게 유지되고, 무한 분기 같은 폭주는 깊이·개수 제한으로 막습니다."

---

### 슬라이드 8 — 도구 생태계 + 검증(Critic) (0:40)

**목적**: 실제로 손에 든 무기가 얼마나 되는지 + 품질 게이트 존재.

**내용**
- 전문가별 도구 수 (현재 구현)
  | 전문가 | 도구 수 | 대표 도구 |
  |---|---|---|
  | edit_expert | 4 | cut_video, merge_video, search_video_segments, cut_by_description |
  | audio_expert | 7 | transcribe, TTS, BGM, SFX, denoise, mix, normalize |
  | text_expert | 5 | 자막, 자동자막, 타이틀, 캡션, 이모지 오버레이 |
  | effect_expert | 2 | apply_remotion_effect, query_effect_catalog |
  | research_expert | 9 | 컨셉/스토리보드/훅/CTA, 웹검색, 유튜브 트렌드/검색/채널분석 |
  - 합계: 실행 도구 **27종** (+ 사전 분석 도구 4종)

### 슬라이드 10 — 데모데이에 무엇을 보여줄까 (0:40)

**목적**: 8월 데모데이 계획 공유. 관객 참여형이라는 점이 포인트.

**내용**

- 확정 방향: **미리 준비한 데모 영상**을 띄워 두고, 관객이 **프롬프트로 직접 편집을 체험**하게 한다
  - 예: "앞부분 지루한 데 잘라줘", "자막 넣어줘", "쇼츠로 바꿔줘"
  - 입력 → 에이전트가 계획을 보여주고 → 즉석에서 결과를 뽑아 비교
- 효과: 관객이 손으로 만져보며 "말로 편집된다"를 체감 → 기억에 남는 데모

**시각·레이아웃 메모**: 좌측 "준비된 데모 영상", 우측 "관객 프롬프트 입력 → 결과" 체험 루프 다이어그램.

**발표 멘트**: "데모데이에는 관객이 직접 써보게 할 겁니다. 처음엔 관객이 찍어온 영상을 편집해 줄까 했는데, 영상을 가져온다는 보장이 없더라고요. 그래서 저희가 데모 영상을 미리 준비해 두고, 관객이 프롬프트만 입력하면 즉석에서 편집해 주는 체험 부스 형태로 갑니다. 말로 영상이 편집되는 걸 직접 만져보는 게 제일 강한 데모라고 봤습니다."
