## 02 · 왜 영상 편집 에이전트인가 (0:40)

`[화면]` 좌: 사람이 직접 편집 / 우: 말로 시킴

> 영상 편집 해보신 분들은 아실 텐데, 컷 따고 자막 싱크 맞추고 타임코드 잡는 게 대부분 반복 작업입니다.
> 자동 편집 툴이 없는 건 아닙니다. 근데 정해진 템플릿에 끼워 맞추는 거라 원하는 대로는 잘 안 나옵니다.
> 실제로 편집을 해 보면 "이 부분 잘라줘, 좀 더 짧게, 오케이", 이 흐름입니다. 결국 대화입니다.
> 이런 반복 대화는 에이전트가 제일 잘 맞는 일입니다.
> 그래서 질문이 단순했습니다. 코딩 에이전트는 되는데, 영상 편집 에이전트는 왜 안 되겠냐.

## 03 · 정적 그래프가 아닌 ReAct 루프 (0:45)

`[화면]` supervisor ReAct 루프 의사코드 + Claude Code 대응표

> 기술적으로 저희가 어디서 갈렸는지부터 말씀드리겠습니다.
> 보통 에이전트 그래프는 노드랑 엣지를 미리 다 정해 둡니다. 그러면 아무리 잘 짜도 흐름이 고정입니다.
> 분석 다음 계획, 계획 다음 실행, 이렇게 박아두면 예상 밖 요청이 들어왔을 때 거기서 막힙니다.
> 저희는 반대로 갔습니다. 도구를 넉넉하게 만들어 두고, 매 턴 어떤 도구를 쓸지는 LLM이 그때그때 정합니다.
> 오른쪽 표를 보시면, 코드 에이전트가 코드를 읽고 고치고 테스트하면서 스스로 도는 구조를,
> 저희는 구간 검색하고, 자르고 붙이고, critic으로 검증하는 걸로 옮겼습니다.
> 모델은 gemini-3.5-flash 하나로 통일했고, 노드마다 temperature만 다르게 줬습니다.

**[질문 대비 · ReAct]** "ReAct는 너무 옛날 논문 아니냐"가 나오면:
> 루프 자체가 오래된 건 맞습니다. 근데 루프는 새로 만들 부분이 아닙니다. 이미 다들 쓰는 방식이라 그대로 가져다 씁니다. 저희가 새로 짠 건 루프 바깥입니다. 전문가를 격리해서 부르는 거, 계획 승인 받는 거, critic으로 재시도 도는 거. 새로운 건 여기입니다.

## 04 · 5개 노드로 이어지는 전체 흐름 (1:00) — 핵심

`[화면]` analysis → script → interrupt_gate → supervisor → critic + 전문가 5종

> 전체 흐름은 노드 다섯 개입니다.
> 먼저 analysis에서 영상을 미리 분석해 컨텍스트를 만들고, script에서 사용자 명령을 단계별 편집 계획으로 바꿉니다.
> 그 계획을 interrupt_gate에서 사용자한테 한 번 보여주고 승인을 받습니다. 여기가 사람이 개입하는 지점입니다.
> 승인되면 supervisor가 전문가 에이전트 다섯을 불러서 실제 편집을 돌리고, 마지막에 critic이 결과를 검증합니다.
> 통과 못 하면 supervisor로 돌려보내서 다시 합니다.
> 하나만 짚으면, 이 다섯 노드는 고정입니다. 그 안에서 어떤 전문가를 어떤 순서로 조합할지가 매번 바뀝니다.
> 이게 아까 말한 ReAct 루프가 실제로 도는 방식입니다.

## 05 · 4개 엔진의 사전 분석 (0:50)

`[화면]` Whisper · Gemini · Claude Vision · FFmpeg → VideoContext로 통합

> 편집을 잘하려면 영상을 제대로 이해해야 합니다. 그래서 분석 엔진을 네 개 붙였습니다.
> Whisper로 단어 단위 타임코드를 밀리초까지 뽑고, Gemini로 씬 경계랑 감정, 흐름을 잡습니다.
> Claude Vision으로 프레임 안의 객체랑 표정 디테일을, FFmpeg로 침묵 구간이랑 볼륨 프로필을 봅니다.
> 엔진마다 잡아내는 게 다릅니다. 이 결과를 타임스탬프 기준으로 하나로 합치면,
> 장면이랑 대사, 감정, 소리까지 담긴 VideoContext가 나옵니다.
> 14분 45초짜리 레퍼런스 영상을 돌리면 단어 351개, 씬 37개, 인물 20명, 하이라이트 후보 6개가 나옵니다.
> "차가 지나간다"가 아니라 "운전자가 전방을 보고 있다"까지 잡습니다.

## 06 · 계획 생성과 사용자 승인 (0:45)

`[화면]` script가 만든 plan JSON + interrupt_gate 승인/수정 분기 + 자동 생성 질문

> 사용자가 명령을 줘도 바로 자르지 않습니다.
> 먼저 "이렇게 편집할 계획이다"를 단계별 JSON으로 만들어서 보여줍니다.
> 그리고 애매한 건 거꾸로 물어봅니다. 자막을 직접 쓸지 자동으로 뽑을지, 배경 음악을 넣을지, 골 장면을 슬로우모션으로 강조할지 같은 겁니다.
> 이때 LangGraph의 interrupt로 그래프를 멈추고 사용자 응답을 기다립니다.
> 승인하면 supervisor로 넘어가고, 수정 피드백이 오면 script로 돌아가서 계획을 다시 만듭니다.
> 편집은 한 방에 끝나는 경우가 거의 없습니다. 이 확인 루프가 사실 제일 중요합니다.

## 07 · 부모를 못 보는, 격리된 전문가 (1:00) — 핵심

`[화면]` supervisor가 spawn하는 전문가 5종(점선=격리) + envelope/result 계약 + 가드레일

> 여기가 저희 구조에서 제일 신경 쓴 부분입니다.
> supervisor가 전문가를 부를 때, 그 전문가는 빈 상태로 새로 뜹니다. 부모가 뭘 하고 있었는지, 대화 기록을 전혀 못 봅니다.
> 넘겨받는 건 딱 두 개입니다. 해야 할 일을 적은 task 문장 하나, 그리고 자기 도메인 도구뿐입니다.
> 일 끝나면 결과만 문자열로 돌려주고 없어집니다.
> 왜 이렇게까지 격리하냐면, 흔히 쓰는 handoff 방식은 메시지 기록을 통째로 공유합니다.
> 그러면 컨텍스트가 길어져서 비용도 커지고 서로 헷갈립니다. 격리해 두면 전문가마다 자기 일만 하고, 컨텍스트가 안 섞입니다.
> 대신 전문가가 전문가를 계속 부르면서 무한히 갈라질 수 있으니까 상한을 뒀습니다.
> spawn 깊이는 2까지, 한 번에 띄우는 child는 5개까지, child 하나가 도는 도구 호출은 12번까지입니다.

## 08 · 27종의 도구, 2단계 검증 (0:40)

`[화면]` 전문가별 도구 수 표(edit 4 / audio 7 / text 5 / effect 2 / research 9) + critic 2단계

> 전문가들이 실제로 쓰는 도구는 지금 27개입니다.
> edit이 4개, audio가 7개, text가 5개, effect가 2개, research가 9개입니다.
> 자르고 붙이는 것부터 음성 합성, 자막, Remotion 이펙트, 트렌드 리서치까지 들어가 있습니다.
> 그리고 결과를 그냥 내보내지 않습니다. critic이 두 단계로 봅니다.
> 먼저 기계적으로, 최종 파일이 디스크에 진짜 만들어졌는지부터 확인합니다. 경로 자체가 없으면 LLM도 안 부르고 바로 재시도로 보냅니다.
> 그다음에 LLM이 계획대로 됐는지를 봅니다. 통과하면 최종 mp4, 못 하면 supervisor로 되돌립니다.
